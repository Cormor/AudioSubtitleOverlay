# 多路识别方案（待实现）

## 已确定的交互

- 多路字幕进入同一个浮窗，按音频时间排列并标注来源；每段原文和译文保持配对。
- 语音模型单独选择；参数预设不包含模型、计算设备、音频来源或语言。
- 先支持两路由用户选定的应用。来源可锁定，不因为另一个程序有背景音就改变识别对象。
- 显示每一路实际采集的应用、监听状态和延迟；暂停或隐藏一路不影响其他路。

## 代码需要怎样拆分

现有应用只维护一个采集对象、一段音频缓冲和一份字幕合并历史；直接启动多个现有流水线会各自加载模型，并产生相同的段落编号。

- 每路维护独立的音频缓冲、语音活动状态、识别上下文和会话编号。
- 识别事件携带来源 ID、路内段落 ID、会话编号和统一时钟下的音频时间。不能按识别完成时间误排不同来源，也不能用相同段落编号覆盖另一来源。
- 单个段落的后续修订原位更新，不把每次修订当成一条新字幕。
- 同一模型和设备优先共用模型服务；公平调度各路任务。语音活动检测减少静音计算，但不保证完美区分音乐与人声。
- 音频和待处理任务都要有边界；只合并同一路的过期触发点，不清掉另一来源的未处理声音。过载时显示状态，不悄悄丢字或无限排队。
- 翻译的排序、取消和过期结果检查都按来源和会话区分。
- 浏览器按应用进程树组织来源，避免窗口进程与实际发声子进程匹配不上；同一进程树不重复采集。

## 速度与验收

多路不意味着识别会更快。先比较单路、双路轮转和有限并行的实际延迟，再决定并发度；不因开启两路就默认加载两份模型。

需要验证：两路同时说话、只有一路说话、一静一响、应用重启、切换来源、暂停恢复、同名段落互不覆盖、译文迟到、错误仅影响本路、游戏负载下每路输入终点和末词到上屏耗时，以及历史按音频时间排列。

## 依据

- [微软应用回环示例](https://learn.microsoft.com/en-us/samples/microsoft/windows-classic-samples/applicationloopbackaudio-sample/) 支持限定进程树采集；这不等于当前程序已经具备多路功能。
- [CTranslate2 Whisper 参数](https://opennmt.net/CTranslate2/python/ctranslate2.models.Whisper.html) 提供并行 worker 和队列控制；是否提高本项目的实时速度仍需实测。
